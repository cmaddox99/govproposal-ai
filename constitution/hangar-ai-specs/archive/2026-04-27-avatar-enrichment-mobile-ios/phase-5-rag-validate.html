What This Phase Does

Phase 5 simulates what an AI coding agent's RAG retrieval would return when it loads these avatars into context. Five canonical queries are run against every avatar. If retrieval fails — file not findable, token budget blown, phantom law ID cited — it surfaces here before we commit. Any BLOCKING query failure routes back to Phase 4.

🎓 Teaching Point — Why RAG Validate catches what Phase 4 misses

Phase 4 focuses on content: did we enrich the right journeys, use cases, and examples? Phase 5 focuses on retrievability: is each file independently queryable within the 3,500-token response window? Phase 5 is the safety net that finds these. The fixes were applied before final verdicts were issued — that is the correct workflow.

🎓 Teaching Point — The companion file pattern

Every guidance.md trimmed in this phase has a companion guidance-detail.md alongside it. The trim file is agent-facing: dense signal, within the RAG token window, structured for retrieval. The detail file is human-facing: full law breakdowns, journey maps, personas, benchmarks. Agents load the trim. Humans read the detail. Neither loses information — they serve different readers.

🎓 Teaching Point — Phantom laws are the hardest bug to catch

The schedule-change-self-serve guidance prose cited ENG-9.4 and ENG-2.3 — both removed from the manifest in Phase 4 — because the manifest and the prose are separate files. Fixing one does not fix the other. Phase 5 Q1 (law coverage) and Q3 (guidance retrieval) together surface this pattern. When you remove a law from a manifest, grep the full avatar directory for that law ID before declaring the fix done.
