Greenfield Development Workflow

Eight phases to build a new system under constitutional AI governance from the first commit — ENG-4.1 ⛔ TDD enforced at every phase gate.

🎯 When to Use Greenfield DC-08

Read this before starting. Choosing the wrong workflow wastes a sprint.

✅ Use Greenfield when…

  • ✅ Building a net-new service, API, or module from scratch
  • ✅ No existing code to characterise — clean slate
  • ✅ Constitution has already been adopted (AGENTS.md + hangar-ai-specs/ exist)
  • ✅ You have a defined bounded context and domain model

❌ Do NOT use Greenfield if…

  • ❌ The code already exists — use Legacy Rescue instead
  • ❌ The repo is not adopted yet — run Adoption first
  • ❌ You haven't defined your domain — Phase 1 will scaffold it, but you need a starting concept
🎲
DC-11 Non-Determinism

Greenfield output varies between runs

Domain models, API contracts, and test structures the agent produces are starting proposals — not final designs. At Phase 2 (Spec), you MUST review and approve the constitutional spec before any code is written. The spec is the constitution of your new service.

Every subsequent phase is governed by it. If the spec is wrong, everything built on top of it is wrong. Treat Phase 2 approval as a non-negotiable human checkpoint.

⛔

⛔ ENG-4.1 — Tests First. Always.

The Greenfield workflow enforces TDD: Phase 4 writes failing tests before any implementation. If the agent writes implementation before tests at any phase, OBJECT immediately. This is a non-negotiable constitutional law. A codebase where tests are written after implementation does not comply with ENG-4.1. The PR must not merge.

ENG-4.1 — Tests MUST exist before implementation

If the agent writes implementation code before the test file exists, that is a constitutional violation. Stop. OBJECT. Do not let it proceed until tests are written first.

Key Decisions Summary
Phase Gate type Key decision Constitutional consequence
1 · Domain Domain "Is this the right bounded context?" All subsequent phases are scoped by this decision
2 · Spec Approval "Does this spec accurately govern this service?" Every other phase is measured against this; wrong spec = wrong service
3 · Slice Compliance "Does this slice match the Phase 2 spec?" Scope creep at Phase 3 compounds into every subsequent phase
4 · TDD ⛔ ⛔ ENG-4.1 "Were tests written before code?" Non-negotiable — reject the PR if violated; tests after code is a constitutional breach
5 · API Contract "Does the API match Phase 2 spec?" Undocumented endpoints are uncontracted; they cannot be certified
6 · Security Security "Are all critical security findings addressed?" Open vulnerabilities block certification; BUS laws cannot be waived
7 · Mutation Quality "Score ≥ 90% with surviving mutants reviewed?" Certify only if yes; weak tests mean the service is untested in practice
8 · Ship 🚀 🏁 Delivery "Is the governed trail complete?" Do not merge without it; an incomplete trail means the service has no constitutional history
