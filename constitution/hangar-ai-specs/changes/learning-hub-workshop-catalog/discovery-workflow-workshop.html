Discovery Modes

Exploratory vs Accelerated — When to Use Each

Mode is declared once in Stage A and is immutable for the entire discovery.
EXPLORATORY MODE
Start from Zero

No existing validated problem statement. All 4 PRD-2.1 dimensions must be completed from new evidence.

When to use it

  • Net-new product idea with no prior research
  • Entering a domain the team has never built in
  • Stakeholder mandate with no evidence backing
  • Discovery triggered by a vague complaint or trend

AA Example

disc-2026-001 — "Does the AA Mobile platform comply with the constitutional engineering discipline?" — No prior validation. Full Exploratory run.

ACCELERATED MODE
Pre-Validated Evidence Exists

A validated problem statement already exists — from a prior discovery, stakeholder mandate, or gathered evidence corpus. Cite the source.

When to use it

  • Existing user research or complaint data (like today)
  • Prior discovery already validated a related problem
  • Regulatory mandate with documented evidence
  • Leadership directive backed by business metrics

PRD-2.1 — Problem Validation Law

The Four Dimensions Every Problem Must Pass

All four dimensions must be filled with cited evidence before Stage A exits. No exceptions.
1Problem Exists

What is the pain or gap? Who experiences it? Where is the evidence it exists today?

Good evidence: Verbatim user quotes, support tickets, error logs, audit findings.

2Problem Matters

Why is this significant enough to act on? What is the business impact or user harm if we do nothing?

Good evidence: Revenue impact, churn data, competitor switches, regulatory exposure.

3Problem Is Solvable

Is a solution technically and organisationally feasible? What gives you confidence we can actually fix this?

Good evidence: Existing capabilities, avatar patterns, analogous solutions, technical proof-of-concept.

4Users Will Exchange Value

Will users invest time, money, or behaviour change to solve this? What's the evidence of intent?

Good evidence: Retry behaviour, explicit demand statements, early adopter signals, willingness-to-pay.

⚠️

Each dimension requires at least one SRC-A-NNN inline citation in the problem statement, traceable to a source with a verbatim quote and date. Attribution without evidence is shadow governance.

Product Discovery Workshop · Hangar Wave 47 / 19
Evidence Craft

How to Find Good Evidence

Evidence is not opinion. It has a source, a date, a verbatim quote, and a confidence level.

🟢 High Confidence

  • Verbatim user quote (App Store, support)
  • Signed stakeholder statement
  • Audit finding with evidence
  • Measured metric from analytics
  • Constitution avatar enrichment finding

🟡 Medium Confidence

  • Market research report
  • Prior discovery reference
  • Team retrospective data
  • Inferred from aggregate patterns
  • Secondary research (analyst data)

🔴 Low Confidence

  • Stakeholder "feeling" or opinion
  • Anecdote without broader pattern
  • Competitor assumption
  • Inferred from indirect signals only

Low confidence evidence must be upgraded or replaced before Stage A exits.

Where to Look

External Products

App Store · Google Play · Reddit · Trustpilot · Intercom / Zendesk tickets · NPS verbatims · Session recordings · Funnel analytics · User interviews

Internal / Platform Products

Avatar Mode 4 enrichment findings · `git log` complexity signals · CI failure rates · Deployment frequency · ENG-3.1 scan reports · Team retro action items · Incident post-mortems

ENG-13.1 — NON-NEGOTIABLE

The Render Gate — Nothing Advances Without This

Every stage transition requires a rendered HTML artifact reviewed by a human in a browser. This is not optional.

Why Rendering Matters

Markdown is a draft. HTML is evidence.

A raw markdown file can contain broken citations, unresolved placeholders, and layout issues that are invisible in a text editor. The rendered HTML forces all of these to surface before a stakeholder reviews the document.

The aa-artifact-render tool resolves every [SRC-A-NNN] citation to a card. 0 unresolved = the evidence is complete.

The Gate Command

aa-artifact-render \
  hangar-ai-specs/changes/disc-2026-003/stage-a-initialize.md \
  --laws-dir laws

✓ Rendered: stage-a-initialize.html [10 citations resolved, 0 unresolved]

The Three Decisions

✅ APPROVE

HTML reads correctly. All citations resolve. Content is complete. Record approval in audit log. Stage advances.

🔧 ENHANCE

Specific issues identified. Agent produces a remediation checklist. Fixes are made and re-rendered. Max 3 rounds per stage.

❌ REJECT

Fundamental problem with the evidence or framing. Blocker documented. Discovery does not advance until resolved.

Track B — Take-Home

Meta Prompts — How to Run This Yourself

A meta prompt loads the full constitutional context into an AI session so it can run the workflow without re-explanation.

What a Meta Prompt Contains

The Five Elements

  • Context block — repo paths, discovery ID, mode, avatar
  • Evidence reference — where the source data lives
  • Session structure — what to do, in what order
  • Rules — only cite real laws, render gate required, no push
  • Start signal — the exact phrase that kicks off the session

Why It Works

The AI has no memory between sessions. A meta prompt is the handshake that says: "Here is everything you need to know to run this workflow correctly, right now, for this team." Without it, you start from zero. With it, you start from Stage A.

The Template Pattern

The [team name] is here. We are running [Track A / B / both].

CONTEXT:
- Constitution repo: [path]
- Discovery: [disc-YYYY-NNN] — "[title]"
- Stage A HTML: [path] (rendered, N citations resolved)
- Evidence: [URL or path] — [N complaints, key stats]
- Avatar: [avatar-id] vX.Y.Z + business
- Approver pending: [Name] ([role])

RULES: Only cite laws that exist in the constitution. Render gate is NON-NEGOTIABLE. No git push without confirmation.

Begin when [name] says: "[start signal]."
