# ⚖️ Laws vs Rules: The Critical Distinction

## They Are NOT the Same Thing

```
┌─────────────────────────────────────────────────────────────────┐
│  RULES                              LAWS                        │
│  ─────                              ────                        │
│  • Guidelines, best practices       • Non-negotiable principles │
│  • "You should..."                  • "You cannot violate..."   │
│  • Have exceptions                  • NO exceptions             │
│  • Advisory                         • Enforceable               │
│  • Team decides                     • Committee governs         │
└─────────────────────────────────────────────────────────────────┘
```

**Examples:**

| Rule | Law |
|------|-----|
| "Use dependency injection" | "Never hardcode secrets in code" |
| "Prefer composition over inheritance" | "Tests must exist before merge" |
| "Consider using records for DTOs" | "Cyclomatic complexity ≤ 10" |

**The Test:** If you have to say *"except when..."* — it's not a law, it's a rule.

```
┌─────────────────────────────────────────────────────────────────┐
│                    UNIVERSAL LAWS                               │
│                                                                 │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐            │
│  │  Java   │  │ Python  │  │  .NET   │  │  React  │  ...       │
```

- 🧪 **Testing:** "Tests before code (TDD)" → True for ALL languages

- 🧱 **Architecture:** "Value objects are immutable" → True always

# 🔀 The Two-Layer Model: Laws + Adoptions

## Universal Laws + Tech Stack Context

```
┌─────────────────────────────────────────────────────────────────┐
│  LAYER 1: UNIVERSAL LAWS                                        │
│  ───────────────────────                                        │
│  Owner: Engineering Laws Committee                              │
│  Changes: Amendment process (2/3 majority)                      │
│  Content: Principles that NEVER change by stack                 │
├─────────────────────────────────────────────────────────────────┤
│  LAYER 2: TECHNOLOGY ADOPTIONS                                  │
│  ────────────────────────────                                   │
│  Owner: Teams / Stack Communities                               │
│  Changes: Simple majority                                       │
│  Content: Stack-specific implementations of laws                │
└─────────────────────────────────────────────────────────────────┘
```

**Example: "Value objects must be immutable"**

| Stack | Adoption Implementation |
|-------|------------------------|
| **Java** | `public record Temperature(double celsius) {}` |
| **Python** | `@dataclass(frozen=True) class Temperature:` |
| **TypeScript** | `readonly` modifiers + Zod schemas |
| **C#** | `public record Temperature(double Celsius);` |

**Same law. Different syntax. Committee owns the law. Teams own the adoption.**

# 🔄 The Amendment Process

## Laws CAN Change — But Not Easily

```
┌─────────────────────────────────────────────────────────────────┐
│                    AMENDMENT LIFECYCLE                          │
│                                                                 │
│  DRAFT ──► PROPOSAL ──► REVIEW ──► EVIDENCE ──► VOTE ──► RATIFY│
│    │          │           │           │          │         │   │
│  Author    Committee   Community    Data      Members   Updated│
│  writes    accepts     feedback   required    vote       laws  │
│                                                                 │
│  [1 week]  [3 days]   [2 weeks]  [ongoing]  [1 week]          │
└─────────────────────────────────────────────────────────────────┘
```

**Amendment Types & Thresholds:**

| Type | Threshold | Example |
|------|-----------|---------|
| **New Law** | 2/3 majority + Committee | "Add Property-Based Testing Law" |
| **Modification** | Simple majority + Committee | "Change complexity from 10 to 12" |
| **Deprecation** | 2/3 majority + Committee | "Remove outdated tech requirement" |
| **Clarification** | Committee only | "Fix typo, add example" |

**The friction is intentional.** Easy-to-change laws aren't laws.

# 🎯 Committee's Role: What You Own

## Universal Laws — NOT Tech-Specific Rules

```
┌─────────────────────────────────────────────────────────────────┐
│  ✅ COMMITTEE OWNS                  ❌ COMMITTEE DOESN'T OWN    │
│  ──────────────────                 ────────────────────────    │
│  • Universal engineering laws       • "Should we use Lombok?"   │
│  • Amendment process                • "Tabs vs spaces"          │
│  • Cross-stack consistency          • Framework preferences     │
│  • Evidence standards               • Team-specific workflows   │
│  • Conflict resolution              • Tooling choices           │
└─────────────────────────────────────────────────────────────────┘
```

**Good for Committee:**
- "Should 'no secrets in code' be a law?" ✅
- "What evidence do we need to change a law?" ✅
- "How do we handle conflicts between teams?" ✅

**Not for Committee:**
- "Should Java teams use Lombok?" ❌ → Java adoption guide
- "Which testing framework is best?" ❌ → Team decision

# 🎁 Key Takeaways

## What I'd Recommend as You Take Ownership

1. **Laws have no exceptions** — If it has exceptions, it's a rule
2. **Universal means ALL stacks** — The test: does it apply to Java AND Python AND React?
3. **Adoptions are separate** — Committee owns laws, teams own implementations
4. **Amendment friction is a feature** — Easy-to-change laws aren't laws
5. **AI needs laws** — Consistent guardrails enable consistent output
6. **Fill the empty folders** — Adoptions without content undermine authority

**The structure is solid. Now earn the authority through content and consistency.**
