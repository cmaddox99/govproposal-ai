Round 1 · Opening Arguments
🗣️ Round 1 — Opening Arguments Focus: Does the problem exist? What is the minimum viable citation structure?
👩‍💼
Sarah Chen FOR
Every single coaching engagement, the moment discovery outputs go into a room with a VP or a product leadership team, the first question is: "Where did you get this?" Right now, Stage B has a beautiful format — personas, JTBD, competitive analysis — but if an insight says "users struggle with login," there is zero way to point at the source without digging back through notes or memory. We are asking PMs to defend claims with no ammunition. The fix is simple and structural: a source registry in the frontmatter, referenced inline.
"Right now we give PMs insights without evidence handles. That is a credibility trap we set ourselves."
👩‍🔬
Dr. Priya Nair FOR
In academic and professional research, every claim requires source attribution. The minimum standard is: platform or venue, date of access, sample size, and at least one verbatim quote. We have 372 real user complaints from Shayne and Ken — collected from App Store iOS, Google Play, Reddit, and Trustpilot — with exact dates and ratings. Not citing these is actively wasteful. We should structure Stage B so that every insight block has a citation ID like [SRC-B-001] that resolves to a full source entry. This isn't overhead — it's what makes the insight defensible.
"An uncited insight is an opinion. A cited insight with a verbatim quote is evidence."
🧑‍💻
Marcus Webb CONDITIONS
I agree citations are needed, but I'm worried about the implementation. If we make every insight require a structured frontmatter entry before the discovery can advance, we risk slowing down accelerated discovery runs. The citation system needs to be designed for speed. My condition: the source registry must be addable incrementally — you can start with a URL and a description, and the record count and verbatim quotes can be enriched as the stage progresses. The exit gate check should require at least one verbatim quote per insight category, not per individual insight.
🧑‍⚖️
James O'Brien FOR
BUS-7.1 requires an audit trail for every stage transition — but an audit trail is only meaningful if the evidence it cites is traceable. Right now, Stage B can advance with the statement "3 user insights validated" and no citation of where those insights came from. That fails a downstream audit. We need machine-readable citation IDs in the frontmatter. The structure: source_registry list with ID, label, platform, URL, retrieval date, record count, and description. Each insight references one or more IDs. The rendered artifact shows the registry as a card panel. This is an audit trail — not a nice-to-have.
"BUS-7.1 audit trail without source citations is an audit trail of conclusions, not evidence."

Round 2 · Refinement & Convergence
🗣️ Round 2 — Refinement Focus: Exact schema, exit gate conditions, rendering requirements
👩‍🔬
Dr. Priya Nair REFINED
Having heard Marcus's concern about speed, I propose the citation structure be split into two tiers: a required minimum (id, label, platform, URL, retrieval date) and an enriched form (record_count, description, sample_quotes array). The exit gate requires at least the minimum for each source cited. The enriched form is required at Tier 2. This gives accelerated runs a fast path while ensuring Tier 2 deep discoveries are fully sourced. The rendered artifact should show source chips — clickable links with platform icons and record counts.
"Minimum fields: id, label, platform, url, retrieved. Enriched: record_count, sample_quotes. Tier 1 needs minimum; Tier 2 needs enriched."
👩‍💼
Sarah Chen ALIGNED
That tiered structure works for coaching too. When I'm pairing with a PM in a Wave 4 Engage session, I can say: "Start with the source registry minimum — just drop the URL and give it an ID. Then we fill in the quotes together as we read through the evidence." The key thing for coaching is the inline citation syntax. Every insight statement in the prose body should carry a [SRC-B-NNN] reference that renders as a clickable chip in the HTML artifact. That way, a VP can hover over a chip and see exactly where the insight came from — platform, date, URL. That answers the question before it's asked.
🧑‍💻
Marcus Webb ALIGNED
I'm satisfied with the tiered approach. One addition: the source_registry should include a methodology_note field at the top level — a short sentence explaining how the evidence was collected. For Shayne and Ken's dataset, this would say something like: "372 complaints filtered from 1,009 voice records via three-gate keyword, sentiment, and context filter." That context is essential for anyone who asks "how were these reviews selected?" It also satisfies PRD-3.1's research methodology documentation requirement.
"A methodology note isn't bureaucracy — it's the difference between evidence and anecdote."
🧑‍⚖️
James O'Brien FINAL APPROVAL
Agreed on all points. For audit purposes, I want one additional exit gate item explicitly added to Stage B: "source_registry populated — all cited sources have minimum required fields (id, label, platform, url, retrieved); verbatim quote provided for each insight category." This makes it unambiguous in the BUS-7.1 audit event. The discovery cannot advance to Stage C without this. The rendered HTML must show a Source Registry card in the sidebar, not buried in the prose. Stakeholders look at the sidebar first.
"Source registry in the sidebar. Non-negotiable from an audit trail perspective."

Stage C — Code Evidence: Evidence Traceability Glossary
Should every quantitative claim and critical finding in Stage C be tied to a source file, section, and verbatim quote — enforced via an evidence glossary?

Phase 2 · Jury Panel
🧑‍💻
Alex Torres
Engineering Lead · iOS Platform
Reviews Stage C evidence as the technical approver. Has challenged discovery outputs when claims like "80 god objects" or "2,286 LOC file" appeared without file paths. Wants verification paths, not just assertions.
Bias: Evidence must be independently verifiable. Claims without paths are opinions.
👩‍💼
Keisha Brown
Director of Product · Mobile Platform
Executive sponsor for discovery. Reads Stage C outputs to make investment decisions. Has had engineers push back on claims in Discovery Gate reviews, causing the entire discovery to lose credibility.
Bias: Evidence challenges happen in the room. The glossary is defensive armor.
🧑‍🏫
David Park
Senior Engineering Coach · Hangar
Teaches teams how to use the constitution. Sees Stage C as the stage where engineering teams most commonly get confrontational ("the AI made this up"). Wants the glossary to teach a verification mindset.
Bias: The glossary is pedagogical — it teaches teams to verify before they act.
👩‍🔧
Nina Russo
Quality Engineering Lead
Responsible for code quality standards. Has seen tech debt inventories that cite "architectural debt" without pointing to a single file. Wants each tech debt item to carry an evidence_ids array.
Bias: Unverified claims in tech debt inventories lead to misallocated engineering investment.
Round 1 · Opening Arguments
🗣️ Round 1 — Opening Arguments Focus: Current state of Stage C claims and minimum glossary requirements
🧑‍💻
Alex Torres FOR
Let me be direct. When I reviewed our last Stage C output, there were claims like "BookingViewModel.kt has 2,286 LOC and uses three mixed reactive frameworks." That's a verifiable claim. But the tech debt table just said "BookingViewModel — mixed reactive frameworks — HIGH severity" with no pointer. If I'm the Engineering Lead approving Stage C, I need to be able to run wc -l app/booking/BookingViewModel.kt and get 2,286. The glossary needs: claim ID, the claim text, source file path, section, and a verbatim quote from the source document. That's my minimum.
"A claim without a file path is not code evidence — it is a rumor about code."
👩‍💼
Keisha Brown FOR
From the product side, I've seen Stage C outputs used in executive briefings where an engineering VP questions a specific number. Right now, the coach or PM has to scramble to find the source — and that panic is visible to the room. If every critical finding in Stage C has a glossary entry, the response is simply: "Evidence ID EVI-C-003, source file reports/android/executive-summary-android.md, section §1, quote on screen." That's composure. That's credibility. The glossary is a product coaching tool as much as a governance tool.
"When you can cite evidence ID and file path in real time, the room stops challenging and starts listening."
🧑‍🏫
David Park CONDITIONS
I support the glossary concept, but I want to be careful that we don't create a system where coaches spend more time writing glossary entries than doing actual discovery. My condition: the glossary must be co-generated — the agent writes the initial entries from the evidence corpus it analyzed (the code quality reports, the statechart analyses), and the human coach reviews and approves them. The agent has already read the reports; it should extract the claims and source references automatically. The human gate is verification, not authorship.
👩‍🔧
Nina Russo FOR
Every item in the tech debt inventory should have an evidence_ids array — even if it's a single entry. The glossary should also include a verification_method field: how was this claim verified? Options could be "direct file inspection," "automated metrics extraction," "code quality report cross-reference," or "manual code review." This field teaches verification culture — when teams see it, they understand that every claim went through a process. That's the pedagogical value David is talking about.
"verification_method is not a checkbox. It is a commitment to a standard of proof."
Round 2 · Refinement & Convergence
🗣️ Round 2 — Refinement Focus: Glossary schema, tech debt linkage, rendered output, exit gate
🧑‍💻
Alex Torres REFINED
Based on what Nina said, here is the glossary schema I'd approve: id (EVI-C-NNN), claim (the assertion being cited), source_file (relative path to the evidence document), section (section heading or §label), quote (verbatim extract from source), verified_by (name or system + date), verification_method (one of the four methods). And in the tech debt table, each row gains an evidence_ids field. The rendered HTML shows the glossary as a collapsible table — not hidden, but not dominating the flow.
🧑‍🏫
David Park ALIGNED
I've accepted the agent-generated first-draft model. The important thing is that the exit gate explicitly requires human review of each glossary entry — the verified_by field must contain a name, not "GitHub Copilot CLI" alone. An agent can author a claim, but only a human can certify it. I'd add a fifth verification method: "agent-extracted, human-verified" for the common case where the agent generates the entry from the corpus and the Engineering Lead or Product Owner confirms it during the Stage C review.
"Agent authors the draft. Human certifies. That's the model."
👩‍💼
Keisha Brown ALIGNED
One thing I want added to the rendered output: an evidence confidence indicator for each glossary entry. If the source is a direct file inspection (wc -l, grep), confidence is High. If it's derived from an AI-assisted quality score, confidence is Medium. If it's extrapolated from indirect signals, confidence is Low. This is not about doubting the AI — it's about giving stakeholders the right calibration for each claim. A "High confidence" claim with a file path is different from a "Medium confidence" claim from an aggregate score.
"Confidence level is part of the evidence contract, not a weakness disclosure."
👩‍🔧
Nina Russo FINAL APPROVAL
I'll add the confidence field to the schema: confidence — High / Medium / Low with a required rationale. That resolves Keisha's concern and adds epistemic honesty to the glossary. One last thing: the evidence glossary should be referenced in the Stage C exit gate alongside "no unreviewed critical findings." The full exit gate item should read: "Evidence glossary populated — all critical findings and tech debt items carry at least one EVI-C-NNN entry with source file, quote, verification method, and confidence level."
